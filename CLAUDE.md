# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is an STM32G431 embedded firmware project for a Raspberry Pi shield that controls a mobile robot. The codebase implements motor control with PID feedback, odometry using encoders, and a state machine architecture for movement control. The robot uses differential drive with two independently controlled motors.

## Build System & Toolchain

### Requirements
- **CMake** (minimum 3.22)
- **Ninja** build system
- **arm-none-eabi** toolchain (ARM cross compiler)
- **STM32CubeMX** for peripheral configuration and code generation

### Building

The project uses CMake presets defined in [CMakePresets.json](CMakePresets.json):

```bash
# Configure for Debug build
cmake --preset Debug

# Build Debug configuration
cmake --build --preset Debug

# Configure and build Release
cmake --preset Release
cmake --build --preset Release
```

Build outputs are located in `build/Debug/` or `build/Release/` depending on configuration.

### Flashing

Flash the firmware using OpenOCD:
```bash
./flash_debug.sh
```

This flashes `build/Debug/shield_raspberry_main.elf` to the STM32G431 via ST-Link.

## Code Organization

### Directory Structure

- **Core/** - STM32CubeMX generated HAL initialization code (auto-generated, do not manually edit)
- **Drivers/** - HAL drivers (auto-generated by CubeMX, NOT tracked in git)
- **User/Inc/** - All manually written header files
- **User/Src/** - All manually written source files
- **cmake/** - Build system configuration including toolchain files

### Important: CubeMX Workflow

**When cloning this repo or modifying the .ioc file:**
1. Open [shield_raspberry_main.ioc](shield_raspberry_main.ioc) in STM32CubeMX
2. Generate code to create the `Drivers/` directory and update `Core/`
3. The `Drivers/` folder is intentionally not tracked by git to save space

**When adding new .c files in User/Src/:**
- Manually add the file path to `target_sources()` in [CMakeLists.txt](CMakeLists.txt) (around line 49)

## Architecture

### State Machine System

The codebase uses two complementary state machine implementations:

#### 1. Generic State Machine ([state_machine.h](User/Inc/state_machine.h))
A simple generic state machine with wake/run/stop callbacks. Used as a foundational pattern.

```c
struct State {
    StateCall wake;   // Called when entering state
    StateCall stop;   // Called when exiting state
    StateCall run;    // Called each update cycle
};
```

#### 2. Movement State Machine ([mv_statemachine.h](User/Inc/mv_statemachine.h))
A queue-based state machine specifically for robot movement control with a construction queue pattern:

- **Construction Queue**: Build a sequence of movement states offline
- **Active Queue**: Currently executing state sequence
- **Maximum 4 states** can be queued (MV_STATEMACHINE_LENGTH)

**Key workflow:**
1. `MSM_reset_construction()` - Clear construction queue
2. `MSM_enqueue_state()` - Add states to construction queue
3. `MSM_ready_construction()` - Flag queue as ready
4. `MSM_update()` - Executes active states, loads construction queue when ready
5. `MSM_set_state_finished()` - Current state signals completion, advance to next

**Available movement states** ([mv_statemachine_states.h](User/Inc/mv_statemachine_states.h)):
- `MV_STATE_HOLD` - Hold position using PID control
- `MV_STATE_TRANSLATION` - Trapezoidal profile straight-line movement

### Motor Control Architecture

**Motor Control Pipeline:**
```
Command → PID Controller → Motor Driver → Motors
                ↑
            Encoder Feedback
```

#### Components:

**1. Motors** ([motors.h](User/Inc/motors.h))
- `MotorHandle` struct wraps PWM timer and direction GPIO
- `motor_drive()` accepts -100% to +100% speed

**2. Encoders** ([encoders.h](User/Inc/encoders.h))
- `Encoder16Handle` provides 32-bit count from 16-bit timer with overflow tracking
- Detects when close to overflow/underflow for safety
- Tracks delta between updates for velocity calculation

**3. PID Controller** ([pid.h](User/Inc/pid.h))
- Full-featured PID with:
  - Individual P/I/D contribution limits
  - Output clamping (min/max)
  - Derivative filtering to reduce noise
  - Integral decay to prevent windup
- `PidSettings` - Configuration (Kp, Ki, Kd, limits, etc.)
- `PidRuntime` - Runtime state (p, i, d, last_err)

**4. Motor Asserv** ([motor_asserv.h](User/Inc/motor_asserv.h))
- `motor_drive_pid()` - Closed-loop control combining PID + motor + encoder
- Takes target RPS (revolutions per second) and applies PID to reach it

**5. Robot Data** ([robot_data.h](User/Inc/robot_data.h))
- Central configuration for robot physical parameters:
  - Wheel diameter
  - Wheelbase width
  - Calibration coefficients
- Global instances: `encoder_R`, `encoder_L`, `motor_R`, `motor_L`
- **Must call `robot_data_init()` at startup**

### Additional Components

**AX Controller** ([ax_controller.h](User/Inc/ax_controller.h))
- Library for controlling Dynamixel AX servo motors (AX-12A)
- Implements Dynamixel Protocol 1.0
- Provides enums for control table addresses and read/write functions

**Recorder** ([recorder.h](User/Inc/recorder.h))
- Debugging tool to capture control loop data
- Stores target/drive/actual values in circular buffers
- `recorder_print_recorded_data()` outputs via printf/UART

**UART Messenger** ([uart_messenger.h](User/Inc/uart_messenger.h))
- UART communication handling with interrupt callbacks

## Development Workflow

### Main Entry Point

The user code entry point is in [Core/Src/main.c](Core/Src/main.c). User code sections are marked with `/* USER CODE BEGIN */` and `/* USER CODE END */` comments. Code outside these sections will be overwritten by CubeMX.

### Debugging

- UART3 is configured for printf debugging (huart3)
- `__io_putchar()` redirects printf to UART3
- Use `recorder` module for capturing control loop data

### Git Branches

- **main** - Main stable branch
- **statemachine_V2** - Current development branch (active)

When creating pull requests, target the `main` branch unless otherwise specified.
